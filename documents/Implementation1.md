Implementation Walkthrough: Hybrid Query Discovery
This document summarizes the implementation of Phase 2: Query Pattern Discovery from the migration methodology. We have successfully implemented a hybrid approach that combines ER-based inference with log-based frequency analysis.

Overview of Components
We have built a pipeline that transforms a raw SQLite schema into a prioritized list of Cassandra-ready query patterns.

1. Schema Extraction (
schema_extractor.py
)
Purpose: Extracts metadata from the SQLite source database.
Result: a JSON object containing tables, columns, primary keys, and foreign key relationships.
2. Phase A: Candidate Query Generation (
candidate_query_generator.py
)
Purpose: Implements the ER-Based Inference algorithm.
Logic:
Iterates through all tables to generate get_X_by_pk queries.
Iterates through 1:N relationships to generate get_child_by_parent queries.
Iterates through M:N junction tables to generate get_related_by_join queries.
Output: 
output/candidate_queries.json
 (A theoretical list of ALL possible access patterns).
3. Query Log Simulation (
query_log_generator.py
)
Enhancements Made:
Column Extraction: Added regex logic to parse SELECT * and return specific column lists from the schema. This is critical for Cassandra table design which requires explicit columns.
Standardization: Updated the simulated query IDs (e.g., get_tracks_by_album $\to$ get_tracks_by_albums_fk) to match the IDs generated by the Candidate Generator.
Output: 
output/query_log.json
 (Simulated usage data with realistic frequency distribution).
4. Phase B: Prioritization (
query_prioritizer.py
)
Purpose: Merges the theoretical candidates with actual usage data.
Logic:
Reads 
candidate_queries.json
.
Reads 
query_log.json
.
Calculates frequency percentage for each candidate.
Assigns Priority:
HIGH (>10%): Candidates for dedicated tables.
MEDIUM (>2%): Candidates for dedicated tables or SAI.
LOW: Candidates for SAI or ignored.
Final Output: output/prioritized_queries.json
Current Status
We now have a Prioritized Query Catalog. The next step in the methodology is Step 3: Logical Data Model Design, where we will take these high-priority queries and design the specific Cassandra tables (Optimization, Denormalization, Partition Keys) for them.
